# Recreate a task's sandbox

Issue: https://github.com/icholy/gritz/issues/1541

## Problem

A task is bound 1:1 to the sandbox its taskstate record references. `Runner.Start`
resolves that record and passes the handle to `backend.Launch` as `reuse`, and the
Docker backend's `ensure` **never** falls through to create: it adopts the exact
recorded container or returns `backend.ErrGone`. That is deliberate — it is what makes
a restart preserve the sandbox's disk.

The cost is that a container that exists but can no longer be started is a dead end.
Every restart re-adopts it and fails identically:

```
adopting existing container task=1541 container=0ea8ada2...
failed to start task ... failed to pre-register with sysbox-fs: Initialization error for container-id 0ea8ada2...
```

Nothing in the API or the web UI drops the binding. The only recoveries today are to
archive the task and wait for `Runner.Prune`, or to get a shell on the runner host and
`docker rm` the container by hand — neither of which is available to a user of the
hosted UI.

## Design

Add a third sandbox-lifecycle command, `RECREATE`, alongside `RESTART` and `STOP`. It
is a restart that first **destroys** the task's sandbox, so the subsequent start takes
the create-fresh path (`reuse == nil`) instead of the adopt path.

The runner already has the whole mechanism: `Runner.Remove` destroys the backend
sandbox and drops the taskstate record, and `Runner.Start` creates a fresh sandbox when
no record exists. What is missing is a way for a user to ask for it.

### Proto

`proto/gritz/v1/gritz.proto`:

```proto
enum TaskCommand {
  NONE = 0;
  RESTART = 1;
  STOP = 2;
  START = 3;
  RECREATE = 4;
}

enum LifecycleKind {
  // ...
  LIFECYCLE_KIND_RECREATED = 11;
}

message TaskActions {
  bool archive = 1;
  bool cancel = 2;
  bool restart = 3;
  bool start = 4;
  bool unarchive = 5;
  bool recreate = 6;
}

service GritzService {
  // ...
  rpc RecreateTask(RecreateTaskRequest) returns (RecreateTaskResponse);
}

message RecreateTaskRequest {
  int64 id = 1;
}

message RecreateTaskResponse {}
```

`tasks.command` is a plain `integer DEFAULT 0 NOT NULL` with no check constraint and
`ListTasksForRunner` filters on `command != 0`, so **no migration is needed** and the
new command reaches the runner through the existing query.

### Model

`internal/model/task.go` gains the command constant (the `stringer`-generated
`taskcommand_string.go` is regenerated by `go generate ./...`):

```go
TaskCommandRecreate TaskCommand = TaskCommand(gritzv1.TaskCommand_RECREATE)
```

and the transition pair, mirroring `CanRestart`/`Restart` exactly:

```go
// CanRecreate returns true if the task's sandbox can be destroyed and rebuilt.
// Same states as CanRestart: recreate is a restart that discards the sandbox
// first, so anything restartable is recreatable.
func (t *Task) CanRecreate() bool { ... same body as CanRestart ... }

// Recreate transitions the task to pending/restarting status and sets the
// recreate command. The version bump orphans the old run's events: the
// destroyed sandbox's supervise goroutine emits a version-scoped "failed"
// that ApplyRunnerEvent rejects, so tearing the sandbox down cannot mark the
// task Failed.
func (t *Task) Recreate() bool {
	if !t.CanRecreate() {
		return false
	}
	switch t.Status {
	case TaskStatusRunning:
		t.Status = TaskStatusRestarting
	default:
		t.Status = TaskStatusPending
	}
	t.Command = TaskCommandRecreate
	t.Version++
	return true
}
```

`Task.Proto` reports `Actions.Recreate: t.CanRecreate()`.

Fold rules (`ApplyRunnerEvent`) — the new command behaves exactly like `RESTART`:

- `applyRunnerEventStarted`: the `Pending/Restarting/Running` arm accepts
  `TaskCommandRecreate` in addition to `Restart`/`Start`, so the new run's `started`
  consumes the command and lands the task in `Running`.
- `applyRunnerEventStopped`: unchanged. Only `Stop`/`Start`/`None` have arms, so a
  `stopped` arriving while `Recreate` is pending returns false — the command survives
  until the new run's `started` consumes it, exactly as for `Restart`.
- `applyRunnerEventFailed`: unchanged — a failed recreate clears the command and lands
  the task in `Failed`.

`LifecyclePayload.Summary` (Go) and `lifecycleSummary` (TS) gain a `Recreated` case.

### Server

`internal/server/apiserver/task.go` gains `RecreateTask`, a copy of `RestartTask` with
three substitutions: `task.Recreate()`, `model.LifecycleKindRecreated`, and the
notification `{Action: "recreated", Type: "task"}` /
`"Task %d sandbox recreate requested."`. Authorization is the existing `OpTaskWrite`
gate — the coarse `AllowOp` pre-check plus the per-row
`Allow(OpTaskWrite, task.ScopeAttr()...)` inside the transaction. The SSE consumer
switches on the resource `type`, not the action, so the web UI invalidates on
`"recreated"` with no client change.

### Runner

A `model.TaskCommandRecreate` arm in `Runner.Poll`:

```go
case model.TaskCommandRecreate:
	g.Go(func() error {
		// Idempotency guard: a record already stamped with the task's current
		// version was written by this recreate's own Start on an earlier poll
		// pass. Destroying now would delete the sandbox we just launched, so do
		// nothing and wait for its "started" to consume the command. Same guard
		// the restart handler needs (proposals/draft/idempotent-restart-handling.md);
		// recreate is strictly more destructive, so it ships with it.
		rec, ok, err := r.store.Read(task.ID)
		if err != nil {
			r.log.Error("recreate: failed to read task record", "task", task.ID, "err", err)
			return nil
		}
		if ok && rec.Version == task.Version {
			r.log.Debug("recreate already processed, waiting for started", "task", task.ID)
			return nil
		}
		// Destroy the bound sandbox and drop the record, so Start takes the
		// create-fresh path. Destroy is force + idempotent, so this covers a
		// running, an exited, and an already-gone sandbox alike.
		if err := r.Remove(ctx, task.ID); err != nil {
			r.log.Error("failed to remove sandbox for recreate", "task", task.ID, "err", err)
			return nil // the command survives; retried on the next poll
		}
		// ... identical to the restart arm from here: sem.TryAcquire, Start,
		// and the "failed" event + slot release on error.
	})
```

Behaviour notes:

- **The old run is force-removed, not drained.** `Destroy` is `ContainerRemove` with
  `Force: true`. Recreate throws the sandbox's disk away by definition, so a SIGTERM
  grace period buys nothing — and `Signal` only *delivers* the signal (it does not wait
  for the exit), so a signal-then-destroy sequence would force-remove the container
  before the driver could act on it anyway. The removed container's `supervise`
  goroutine sees `Wait` return `ExitLost`, releases its semaphore slot, and enqueues a
  `failed` stamped with the **old** version, which `ApplyRunnerEvent`'s version guard
  discards.
- **A failed destroy is retried.** `Runner.Remove` deletes the record only after the
  backend destroy succeeds, and the recreate command survives on the server until a
  `started` consumes it, so the next poll retries. This is why the arm returns early
  instead of falling through to `Start` (which would re-adopt the container we just
  failed to destroy).
- **No record** (already-pruned sandbox): `Remove` is a no-op returning nil, and
  `Start` creates fresh. Recreate is therefore also the natural repair for a task whose
  sandbox vanished underneath it.

### Web UI

- `webui/src/lib/task.ts`: `canRecreateTask(task) => task.actions?.recreate ?? false`.
- `webui/src/components/task-sidebar.tsx`: a `SidebarAction` row under Restart, icon
  `RefreshCw`, label "Recreate sandbox", `destructive`. Because it discards the
  sandbox's filesystem (the clone, any uncommitted work), it is the first task action
  gated behind a confirmation — a small `Dialog` (the primitive is already vendored at
  `components/ui/dialog.tsx`) explaining that the sandbox and its contents are deleted
  and a new one is built from the workspace image.
- `webui/src/routes/tasks.$id.tsx`: `useMutation(recreateTask, { onSuccess: refetchAll })`,
  wired through as `onRecreate` / `recreatePending`.
- `webui/src/components/command-badge.tsx`: `[TaskCommand.RECREATE]: 'recreate'`.
- `webui/src/lib/timeline.ts`: `LifecycleKind.RECREATED` → summary "Recreated sandbox",
  category `'restarted'`.

### Rollout

`Runner.Poll`'s switch has no `default` arm, so a runner older than the command
silently ignores it and the task sits in `Pending` with a stuck command until someone
cancels it. The runner slice therefore lands and deploys **before** the RPC that can
issue the command.

## Implementation Plan

1. **Proto + model** — Delivers: the `RECREATE` command, `LIFECYCLE_KIND_RECREATED`,
   `TaskActions.recreate`, the `RecreateTask` RPC messages, `Task.CanRecreate`/
   `Task.Recreate`, the `started` fold arm, and both `Summary` cases. Regenerates
   `internal/proto`, `taskcommand_string.go`, `client_moq.go`, and `webui/src/gen`.
   Depends on: nothing (no migration — `tasks.command` is an unconstrained integer).
   Verifiable by: `internal/model/task_test.go` cases for the transition (from each of
   running/completed/failed/cancelled, and refused when archived/pending) and for the
   `started` fold consuming the command.

2. **Runner recreate handler** — Delivers: the `TaskCommandRecreate` arm in
   `Runner.Poll` (version guard → `Remove` → `Start`). Dormant until slice 3 — nothing
   can issue the command yet — so it is safe to merge and deploy on its own. Depends
   on: (1). Verifiable by: runner tests with the `backend.BackendMock` asserting that a
   recreate poll calls `Destroy`, drops the taskstate record, and calls `Launch` with
   `reuse == nil`; that a record already at the task's version is a no-op; and that a
   failing `Destroy` leaves the record intact and does not launch.

3. **`RecreateTask` RPC** — Delivers: the server handler, its lifecycle event and
   notification. Depends on: (1), and on (2) being deployed to the runners. Verifiable
   by: an `apiserver` test asserting the task's command/status/version, the emitted
   `RECREATED` lifecycle event, the `PendingRunner` notification, and the
   `FailedPrecondition`/`PermissionDenied` paths.

4. **Web UI** — Delivers: the "Recreate sandbox" sidebar action with its confirmation
   dialog, plus the command badge and timeline labels. Depends on: (3). Verifiable by:
   recreating a wedged task from the task page and watching a fresh container come up.

## Trade-offs

- **A `RECREATE` command vs. a destroy-only `DestroySandbox` RPC.** The issue offers
  both spellings. Destroy-only reads simpler but is more machinery: task commands are
  consumed by the runner events they provoke (`started` / `stopped` / `failed`), and a
  destroy has no such event — clearing the command would need a new runner event type
  and new fold rules. Recreate rides the existing `started` and reuses the restart
  transitions verbatim. It is also the operation people actually want: the container is
  destroyed *so that* the task can run again.
- **A new command vs. making `RESTART` recreate on failure.** Auto-recreating whenever
  an adopt fails would fix this class of wedge with no new API, but it silently discards
  a sandbox's disk on any transient adopt error — exactly the state the reuse path
  exists to protect. Destroying a filesystem should be explicit and user-initiated.
- **Force destroy vs. graceful drain.** Covered above: the disk is going away, and
  `Signal` doesn't wait for the exit, so a graceful pre-pass would be theatre. The
  version guard is what keeps the torn-down run from marking the task `Failed`.
- **Doing nothing (`docker rm` on the host).** Works for a self-hosted operator and is
  what happened on task 1541, but it is unavailable to a hosted user and leaves the
  taskstate record dangling until the next `Load` reconciles it.

## Open Questions

- **Should `CanRecreate` also allow `PENDING` and `RESTARTING`?** As specified it
  mirrors `CanRestart`, which covers the reported wedge (a failed start lands the task
  in `Failed`). Allowing the in-flight states would make recreate a true "unstick me"
  button, but it can race a poll pass that is mid-`Start`: the version bump would orphan
  a container that is already launching. If we want it, it needs its own design.
- **A stale `gritz-{task-id}` container with no record.** `Remove` destroys only the
  *recorded* handle, so if the record was lost while the container survived (a wiped
  taskstate dir, a re-homed runner), the fresh create fails on the Docker name
  conflict. Should recreate additionally delete by name, or is that a separate
  reconciliation concern?
- **Confirmation UX.** No task action confirms today. Is a dialog right, or is
  destructive styling plus an undo-less toast enough?
